## Functionality risks

### High

1. **`apps/web/src/routes/desktop/BinnenBoekenPage.tsx:52-53`** — The entire "Binnen boeken" (goods receipt) page is non-functional. Neither `Concept opslaan` nor `Verwerken` has an `onClick` handler, and no API call exists anywhere in the file (confirmed: `grep -n onClick` on the file shows no handler on either button). A user can fill in the whole receiving form and nothing is persisted — silently. This matches the known-incomplete status noted in `workflows/41-receive-material.md`, but the page is otherwise fully styled and looks finished, so it reads as broken rather than "not built yet." *Fix: wire both actions to a real create/adjust-stock API call, or hide the page behind a "coming soon" state until implemented.*

2. **`apps/web/src/routes/desktop/VoorraadPage.tsx:618` (reservation display) + item drawer** — Reservation counts (`Gereserveerd` column, drawer reservation list) are captured once into `useState` and never refreshed. `ReserveringenPage.tsx` has an explicit `useEffect` fix for this exact staleness; `VoorraadPage` never received the same fix. *Failure scenario:* reserve/complete a saw job elsewhere, return to Voorraad — the reserved-quantity column is stale until a full page reload. *Fix: mirror the refresh effect from ReserveringenPage.*

3. **`apps/web/src/components/relaties/RelatieGegevensTab.tsx:60-95` and `RelatieContactenTab.tsx:18-28`, unmounted by `apps/web/src/routes/desktop/RelatieDetailPage.tsx:184-186`** — Debounced auto-save (400 ms `setTimeout`, cleared via `clearTimeout` on unmount) silently loses edits. Tabs are conditionally rendered (`{tab === 'gegevens' && <RelatieGegevensTab .../>}`), so switching tabs **unmounts** the previous tab, canceling its pending save before it fires. **Confirmed by direct code read.** *Failure scenario:* edit a phone number or address field, click a different tab within 400 ms (a normal fast click) — the edit is discarded with zero error or notification. *Fix: flush the pending save synchronously in the effect's cleanup when the form is dirty, instead of only clearing the timer.*

4. **`apps/web/src/routes/desktop/ArtikelDetailPage.tsx:117-121` (meta) and `:123-145` (estimate)** — Same debounce-vs-unmount pattern as #3, this time on navigating away from the article detail page (breadcrumb, sidebar nav, browser back) within 400 ms of an edit. Any inline field edit or calculator change is lost silently. *Fix: same as #3 — flush on unmount rather than cancel.*

5. **`apps/web/src/api/articles.ts:200-223` (`nextArtNo`, `articlesApi.create`) + `apps/api/src/routes/articles.ts:48-56,75-104`** — The client computes the new article ID itself (`ART-000N`) from its local in-memory cache and sends it to the server, instead of letting the server mint it from the transactional `doc_sequences` counter. Two tabs open at different times can independently compute the same next ID; the second POST fails on a unique-constraint violation, but `articlesApi.create()` swallows the error with `.catch(() => {})`. The UI has already optimistically navigated to `/artikelen/ART-000N` as if it succeeded, and further edits PATCH a row that doesn't exist. *Fix: don't pre-generate the ID client-side for the request — let the server always mint it, or at minimum surface the failure and roll back the optimistic navigation.*

6. **`apps/web/src/routes/desktop/ProjectDetailPage.tsx:139-154`** — Autosave race in the multi-tab/edit-lock project feature: switching to another already-open project tab within ~400 ms of an unsaved meta edit (naam/klant/klantRef/levertijdDatum) cancels the pending debounce before it fires, because the "reset meta for new project" effect and the "debounce persist" effect both key off the same `meta` state. The edit disappears with no save and no warning. *Fix: decouple the reset-on-project-switch effect from the debounce-persist effect, or flush pending saves before switching.*

7. **`apps/web/src/routes/desktop/ZaagCalculatorPage.tsx:85-91` (`committedByBar`)** — Sums `sawLength` from **every** reservation in the store regardless of `status` (`open` / `in_progress` / `done`). **Confirmed:** `reservationsStore.list()` (`apps/web/src/api/reservations.ts:78`) returns the full unfiltered cache, and once a job is completed via Zaagflow the bar's physical `currentStock` is already reduced to the measured leftover — but the now-`done` reservation is never excluded here, so its length gets subtracted a second time. *Failure scenario:* any bar remnant reused after a completed sawing job shows far less (often zero) available material than it physically has, blocking valid reservations. *Fix: filter `allReservations` to `status !== 'done'` before summing.*

8. **`apps/web/src/components/planning-queue/QueueDetails.tsx:26`** — Drops the `onSetHold` (and `onClose`/`onUnplan`) props passed to it. This is the only place these are wired to, so the "hold" (`notBefore`) feature is fully built end-to-end (schema, API route, scheduler, lock-icon rendering) but has no way to be triggered from the UI anymore. *Fix: restore the prop wiring in `QueueDetails`.*

### Medium

9. **`apps/api/src/routes/low-stock.ts:19-20`** — `r.currentStock < r.minStock` compares Prisma `Decimal` objects with JS's native `<`, which falls back to **lexicographic string comparison**, not numeric. **Confirmed:** `new Prisma.Decimal('9') < new Prisma.Decimal('10')` evaluates `false` (should be `true`); a value like `100` vs `99` inverts the other way. This compiles cleanly because TS can't catch it. *Exposure is currently low* — the frontend does not call `/api/low-stock` (it recomputes low-stock alerts client-side in `todoAlerts.ts` using `Number(...)`, correctly), so this bug lives in an orphaned endpoint (see redundancy #1 below) rather than live UI — but it would silently produce wrong low-stock flags the moment anything wires this endpoint up as-is. *Fix: use `.lessThan()`/`.comparedTo()` instead of `<` for Decimal comparisons.*

10. **`apps/api/src/routes/raw-materials.ts`, `movements.ts`, `finished-goods.ts`, `search.ts`** — Several routes return Prisma `Decimal` fields (`lengthMm`, `currentStock`, `minStock`, `amount`, `previousStock`, `newStock`) unconverted, so `JSON.stringify` serializes them as **strings**, contradicting the shared Zod schemas (`RawMaterialSchema.lengthMm: z.number()`, etc.) which declare them as numbers. Other routes (`grades.ts`, `machines.ts`, `articles.ts`, `reservations.ts`) correctly call `.toNumber()` first — the handling is inconsistent. The frontend already had to work around this by defining a parallel `RawMaterialRow` type with string fields (`apps/web/src/api/raw-materials.ts:34-49`) and manually wrapping every access in `Number(...)`. No live crash today because every call site remembered to coerce, but it's a real contract violation and the root enabler of #9. *Fix: apply `.toNumber()` consistently across all routes returning Decimal fields, ideally via one shared serializer.*

11. **`apps/web/src/routes/desktop/VoorraadPage.tsx:58` (`exportToCSV`)** — Exports the full original-length weight instead of the proportional remaining weight (which the stats tile and item drawer compute correctly elsewhere). Overstates weight in the CSV export for any partially-used bar. *Fix: reuse the same remaining-weight calculation used in the drawer/stats tile.*

12. **`apps/web/src/components/raw-materials/RawMaterialForm.tsx:135,138`** — Clearing "Afwerking" or "Locatie" in the edit drawer is a silent no-op: `'' || undefined` drops the key from the PATCH body entirely, so Prisma never updates it and the old value sticks. *Fix: send `null` explicitly for cleared optional fields instead of `undefined`.*

13. **`apps/web/src/api/locations.ts:80`** — `locationsApi.list()` swallows any fetch error (including a 3 s client timeout) and silently falls back to fake mock locations with non-UUID ids; selecting and saving one fails validation with a confusing error far from the actual cause. *Fix: surface the fetch failure (toast/banner) instead of silently substituting fake data.*

14. **`apps/web/src/routes/desktop/VoorraadPage.tsx:21-27,552-571`** — The item drawer's "Historie" panel always shows the same 5 hardcoded `MOCK_HISTORY` rows regardless of which material is open; no real movements API is wired to it despite `apps/api/src/routes/movements.ts` existing and working. *Fix: fetch real movement history for the open item.*

15. **`apps/web/src/components/planning-queue/QueueDetails.tsx:98-100,143-150`** — "Artikel"/"Tekening"/"Verkenner" buttons have no `onClick`, and the "SHIFT" input only updates dead local state — all look actionable but do nothing. *Fix: wire these up or remove them until implemented.*

16. **`apps/web/src/utils/todoAlerts.ts:121` (`getProductionOverrunAlerts`)** — Measures elapsed time from `ProductieOrder.createdAt` (set at offerte acceptance) rather than from when production actually started. Orders that sit queued for a while will falsely trigger "Productie loopt uit" the instant their first step is checked off. *Fix: track and use an actual production-start timestamp.*

17. **`apps/web/src/utils/planningSharedUtils.ts:224-227`** — Ghost/forecast load for an offerte-regel whose `bewerking` name doesn't match any known machine is stored under an empty-string key that the Prognose chart-building code never reads, so that forecast load silently disappears instead of surfacing anywhere (e.g. as "onbekende bewerking"). *Fix: surface unmatched bewerkingen instead of dropping them under `''`.*

18. **`apps/web/src/api/articles.ts:210` (`articlesApi.list()`)** — Unlike every sibling wrapper (`relatiesApi`, `gradesApi`, `machinesApi`, `profilesApi`), which try a live fetch and fall back to cache only on failure, `articlesApi.list()` just returns the in-memory cache — it never calls the API at all outside the one-shot `initArticles()` on page load. TanStack Query refetches on `['articles']` (refocus, invalidation, staleTime) are no-ops. A full reload is the only way one browser tab sees another session's article changes. *Fix: match the try-fetch/catch-to-cache pattern used elsewhere.*

19. **`apps/web/src/routes/desktop/ZaagCalculatorPage.tsx:154`** — `Math.min(maxPieces, stillNeeded || maxPieces)`: when `stillNeeded` is legitimately `0` (quantity already fully covered by other selected bars), the falsy-zero `||` substitutes `maxPieces`, silently pre-filling a full reservation on a bar the user didn't need. Can be submitted unnoticed via "Reserveer assen". *Fix: use `stillNeeded === 0 ? 0 : stillNeeded` or an explicit `??`-style check that only falls back on `undefined`/`null`.*

20. **`apps/web/src/components/projecten/OfferteTab.tsx:55-67` (RegelForm kostprijs suggestion)** — Sums only `external` estimate nodes when suggesting a kostprijs on re-picking an article, ignoring material/machine cost — unlike the shared `buildEstimateCtx`/`computeEstimateTotals` path used by `ArtikelPickerModal`/`RegelsTable`. Low exposure (only fires when re-picking on an existing regel with an empty price) but is a duplicated, incomplete formula. *Fix: reuse `buildEstimateCtx`/`computeEstimateTotals` here too.*

2. **Dead endpoint `GET /api/low-stock`** (`apps/api/src/routes/low-stock.ts`) — no frontend caller (client-side `todoAlerts.ts` reimplements the same check independently and correctly); already self-flagged in `decisions/90-decisions-log.md` (2026-07-02) as parked.
