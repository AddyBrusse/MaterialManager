## Functionality risks

### High

1. **`apps/web/src/routes/desktop/VoorraadPage.tsx:618`** — Reservation counts (`Gereserveerd` column + item drawer) are read once via `useState(() => reservationsStore.list())`, which runs before `initReservations()` (kicked off in `apps/web/src/hooks/useInitAppData.ts:32`) has resolved, and the page never re-reads the store afterward (no listener for the `sm-reservations-changed` event that `AppLayout.tsx` and `ReserveringenPage.tsx` already use). A hard refresh or direct navigation to `/voorraad` reliably shows stale/empty reservation data that never self-corrects. `ReserveringenPage.tsx:266-272` already has the fix pattern (`useEffect` re-fetch); `VoorraadPage` never got it.
   *Fix: subscribe to `sm-reservations-changed` (or re-run `reservationsStore.list()` in a `useEffect` after `initReservations()` resolves), same as `ReserveringenPage`/`AppLayout`.*

2. **`apps/web/src/routes/desktop/BinnenBoekenPage.tsx`** (whole file) — Confirmed to be entirely mock/client-only: hardcoded `SUPPLIERS`/`LOCATIONS`/`RECENT`/`INIT_LINES`, "Concept opslaan"/"Verwerken" buttons with no `onClick` handlers, `totalKg` is a fake `aantal * 100` approximation, and there is no matching `apps/api/src/routes` file at all — no persistence path exists. This is already flagged as a known gap in `workflows/41-receive-material.md:3-9`, so it's not a surprise, but it means the page is functionally a no-op today and worth keeping on the radar since it's a primary receiving workflow.
   *Fix: tracked already in `workflows/41-receive-material.md`; no new action beyond prioritizing it.*

3. **`apps/web/src/api/articles.ts:209-241` and `apps/web/src/api/relaties.ts:109-146`** — `create`/`update` write optimistically to a local cache/localStorage and fire the real network request detached, swallowing failures (`.catch(() => {})` for articles; a fabricated client-only record for relaties). No caller awaits/checks the real HTTP result, and there's no global error toast in `apps/web/src/api/client.ts`. Concretely: `articlesApi.create` computes the new `ART-####` id client-side via `nextArtNo(cache)` rather than the server's atomic sequence (only used when the client omits `id`, which it never does) — if two sessions compute the same id, the POST 500s on the DB unique constraint, silently swallowed, and the UI has already navigated to a "new" article that was never actually persisted; every subsequent edit then 404s just as silently. No "unsynced" indicator exists anywhere in the UI (verified via grep).
   *Fix: don't swallow the network error — surface a notification and roll back the optimistic entry (or block navigation) on failure; let the server assign IDs authoritatively instead of computing them client-side.*

4. **`apps/api/src/routes/low-stock.ts:19-20`** — `r.currentStock < r.minStock` compares Prisma `Decimal` objects directly. Verified empirically against this repo's installed `@prisma/client` runtime that `Decimal.valueOf()` returns a string, so `<` does lexicographic (not numeric) comparison — e.g. `Decimal(200) < Decimal(1000)` evaluates `false` even though 200 is numerically less than 1000. This makes the low-stock filter silently wrong for many digit-length combinations (both false negatives and false positives). Currently low real-world impact because the route has no frontend caller (the "Lage voorraad" sidebar badge is computed independently and correctly in `apps/web/src/utils/todoAlerts.ts`), but it's a live landmine if this endpoint is ever wired up.
   *Fix: use `r.currentStock.lessThan(r.minStock)` (Decimal API) or convert both sides with `Number(...)` before comparing.*

5. **`apps/web/src/routes/desktop/PlanningQueuePage.tsx:78-85` and `apps/web/src/utils/planningSharedUtils.ts:104-141`** — Wachtrij/Prognose match a planned step to its machine by `job.machineNaam === m.name` (string equality against the *current* machine name), and machine names are freely editable in `OverheadTab.tsx:150-153` with no cascade to already-planned steps. Renaming a machine while jobs are queued on it makes those jobs vanish from every machine's Wachtrij panel, the Gantt timeline, and Prognose's heatmap/bars — while `computeQueueKpis` still silently counts them as active minutes, and `isAtRisk` never flags them because the scheduler no longer sees them at all.
   *Fix: key machine matching by `Machine.id` instead of `name`, or cascade-rewrite `geplandMachine` on every affected step when a machine is renamed.*

### Medium

6. **`apps/web/src/components/raw-materials/RawMaterialForm.tsx:132-140`** + **`packages/shared/src/schemas/raw-material.ts:20-31`** *(independently confirmed by two subagents)* — `UpdateRawMaterialSchema`'s `surfaceFinishId`/`locationSlotId`/`minStock` are `.optional()` (undefined-only), not `.nullable()`. The form maps a cleared field to `undefined`, which `JSON.stringify` drops from the request body entirely, so the PATCH never touches that column — clearing "Afwerking", "Locatie", or "Min. voorraad" on an existing item silently fails to persist, with no error shown.
   *Fix: make these fields `.nullable().optional()` in the shared schema, have the form send explicit `null` on clear, and let the route pass `null` through to Prisma (already valid for nullable scalar columns).*

7. **`apps/web/src/routes/desktop/VoorraadPage.tsx:612, 809-916`** — The `['raw-materials']` query has no `isError` handling; on fetch failure the table falls through to the generic "Geen artikelen gevonden" empty state, indistinguishable from a genuinely empty filtered result.
   *Fix: branch on `isError` and show a distinct load-failure message.*

8. **`apps/web/src/routes/desktop/VoorraadPage.tsx:21-27, 143-145, 552-571`** — The item-detail drawer's "Historie" tab always renders a hardcoded `MOCK_HISTORY` array regardless of which item is open (not filtered by `row.id`), and "Meest verbruikt" keys `MOCK_MUTATION_COUNTS` by old mock ids that can never match real Prisma UUIDs. A real per-item history already exists via `GET /movements?itemId=` but isn't used here. Leftover from the pre-2026-06-22 mock phase.

9. **`apps/web/src/components/projecten/OfferteTab.tsx`** (`RegelForm.pickArticle`) — The free-regel price suggestion sums only `external` node costs and doesn't import grades/profiles/machines at all, unlike the correct calculation already used in `ArtikelPickerModal.tsx`/`RegelsTable.tsx`, so material and machine costs are silently omitted from the suggested price.

10. **`apps/web/src/routes/desktop/ZaagCalculatorPage.tsx`** — Reservation state is read once at mount with no listener for the `sm-reservations-changed`/`storage` events other Zaag pages subscribe to, so the committed/available bar can go stale, risking double-booking of material.

15. **`apps/api/src/routes/relaties.ts:57-63`** (DELETE) — does no cleanup of `Article.relatieId`/`Project.relatieId` (plain `String?` columns, no FK/cascade in `schema.prisma`), yet the delete-confirmation dialog in `RelatiesPage.tsx:~152` claims linked articles "lose the link" — they actually keep a dangling, permanently-unresolvable id.

16. **`packages/shared/src/schemas/raw-material.ts`, `finished-good.ts`, `movement.ts`; `grade.ts`** — declare `lengthMm`/`currentStock`/`minStock`/`densityKgM3`/`amount`/etc. as `z.number()`, but the corresponding API routes (`raw-materials.ts`, `finished-goods.ts`, `movements.ts`) return the raw Prisma `Decimal` unconverted, which serializes to JSON as a *string*. `grades.ts` is the one route that does convert (`.toNumber()`). The frontend already works around this by typing these fields as `string` in its own wrapper types (`RawMaterialRow.lengthMm: string`, etc.), so there's no live crash, but `Schema.parse()` on any of these actual responses would throw, and the shared schema is false documentation of the wire format.
    *Fix: pick one convention (recommend: convert Decimal → number in every route, matching `grades.ts`) and apply it consistently.*

17. **`packages/shared/src/schemas/lock.ts:11-19`** — `LockSchema` requires `itemType`/`itemId`, but `GET /locks/:itemId` (`apps/api/src/routes/locks.ts:26-35`) never includes them in its response. No current caller dereferences those fields, so it's latent, not active.
    *Fix: add `itemType`/`itemId` to the route response, or narrow the type to what's actually returned.*

18. **`apps/api/src/routes/articles.ts` and `apps/api/src/routes/reservations.ts`** — `Article` and `ZaagReservering`, both core business entities, have zero shared Zod schema; validation is defined locally with `z` imported directly, bypassing `@stockmanager/shared` entirely — contrary to CLAUDE.md's stated "shared schema → Prisma model → API route → frontend" build order, and the likely origin of the Decimal-serialization inconsistencies above (both routes hand-roll their own `toNumber()` serializers).
    *Fix: extract `ArticleSchema`/`CreateArticleSchema` and `ZaagReserveringSchema`/`CreateReservationSchema` into `packages/shared/src/schemas/`.*

19. **`apps/web/src/utils/todoAlerts.ts:112-119`** (`getProductionOverrunAlerts`) — calls `computeEstimateTotals(article.estimate, ctx)` with the default `qty = 1` (so `totals.timeMin` already includes one setup + one cycle), then multiplies the whole thing by `order.qty` again — double-counting setup time. The canonical calc used elsewhere (`berekenOrderMin` in `planningUtils.ts`) counts setup once: `cycleMin * qty + setupMin`. For a batch order (e.g. qty=10, setup=60min, cycle=10min), the correct overrun threshold is ~160min but this code effectively requires ~700min elapsed before firing — real overruns on batch orders go unreported.
    *Fix: call `computeEstimateTotals(article.estimate, ctx, order.qty)` and use `totals.timeMin` directly without re-multiplying.*

20. **`apps/web/src/components/planning-queue/QueueDetails.tsx:12-28`** — `onClose`/`onUnplan`/`onSetHold` are declared as props (real handlers exist in `PlanningQueuePage.tsx`) but never used in the component body (verified via grep — no other call site for `handleSetHold` exists anywhere). ## Notes on method

Baseline checks (install/typecheck/build/test) were run directly. The deep audit was done by six parallel subagents, one per area (Materiaalbeheer, Stamgegevens, Productie, Planning, a cross-cutting redundancy sweep, and a shared-schema/Prisma-drift sweep), each tracing actual code paths rather than guessing. Two findings above were independently reported by two different subagents working on unrelated areas (the `minStock`/optional-field-clearing bug, and the duplicated weight-calculation formula) — cross-validation, treated as higher-confidence. All findings are anchored to file:line and describe a concrete failure scenario; nothing here is speculative pattern-matching.
