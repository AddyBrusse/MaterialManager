## Functionality risks

### High

1. **`apps/api/src/routes/movements.ts:28-68`** — stock-movement writes have no row lock and no non-negative check, unlike the identical problem already solved elsewhere in this codebase (`apps/api/src/routes/projects.ts:70-77`'s `withProject` does `SELECT ... FOR UPDATE` with a comment explaining exactly this). Two concurrent movements on the same item (two users, or a double-click) can lose an update via stale `previousStock`, and a negative `amount` can drive `currentStock` below zero. Contradicts `features/32-stock-movements.md:36,44` and `workflows/42-adjust-stock.md:31-47`, which require both. **Fix:** reuse the `withProject`-style `SELECT ... FOR UPDATE` pattern and reject when `newStock < 0`.

2. **`apps/web/src/api/raw-materials.ts:120-127` (`adjustStock`) + `apps/web/src/routes/desktop/VoorraadPage.tsx:306-327`** — "Toevoegen"/"Afboeken"/"Correctie" all compute an absolute target client-side from a possibly-stale `['raw-materials']` query cache value and send `kind: 'overwrite'`. Two concurrent additions on the same bar both read the same stale stock, and the second overwrite silently clobbers the first — this happens even if finding #1's server-side lock is added, since the stale value is baked into the request before it reaches the server. **Fix:** send `kind: 'delta'` with a signed adjustment for Toevoegen/Afboeken (per `workflows/42-adjust-stock.md:22-23`), reserving `overwrite` for Correctie only.

3. **`apps/web/src/api/locations.ts:88-127`** — every mutation (`createLocation`, `updateLocation`, `removeLocation`, `addSlot`, `removeSlot`) does `apiFetch(...).catch(() => { <write to local mock>; return { data } })`. `apiFetch` throws on *any* non-2xx response or its abort timeout, not just "offline" — so a genuine validation error or DB failure is silently converted into a fabricated success toast in `LocationsTab.tsx:28-53`, while the write only lands in that browser's `localStorage`, invisible to other users. **Fix:** drop the mock-fallback `.catch()` (per CLAUDE.md's "mock phase ended" decision) and let errors propagate to `onError`.

4. **`apps/web/src/api/{grades,profiles,relaties,surface-finishes}.ts` — `remove()`** (`grades.ts:67-72`, `profiles.ts:93-98`, `surface-finishes.ts:50-55`, `relaties.ts:148-155`) — same pattern as #3: a server-rejected delete (e.g. FK-constrained grade/profile still in use by a raw material) is swallowed and the item is optimistically removed from the local cache anyway, silently misleading the admin until the next real refetch brings it back. Compounded by **`apps/api/src/routes/{grades,profiles}.ts` DELETE** having no handling for Prisma FK-violation errors (`P2003`) — `apps/api/src/middleware/error.ts:4-39` falls through to a generic 500 with no "in use" message. **Fix:** only fall back to local-cache mutation on genuine network failure, not on any rejected server response; add a `P2003` handler in the error middleware returning 409.

5. **`apps/api/src/routes/{search,low-stock}.ts`** query the legacy `prisma.finishedGood` table, but the current Artikelen UI writes exclusively to the separate `Article` model (`apps/api/src/routes/articles.ts`) — nothing creates/updates `FinishedGood` rows anymore. Global search's "finished goods" results and the Todos low-stock alerts (`apps/web/src/utils/todoAlerts.ts:45-67`) can never reflect real Articles, so low-stock alerts for real make-to-stock articles are silently missing. Documented as a known, unreconciled drift in `features/31-items-finished.md:8-13`. **Fix:** point these routes at `Article`, or remove the `finished` code paths and the `FinishedGood` model/route/wrapper once confirmed fully unused.

6. **`apps/web/src/api/reservations.ts:80-96` vs `apps/api/src/routes/reservations.ts:69-85`** — the frontend generates its own reservation id client-side and never reconciles it with the server's independently-generated id (the POST response is discarded — `.catch(() => {})`, no `.then()`). Every subsequent mutation (`remove`, `setPriority`, `applyPlan`, `setStatus`, `complete` — used throughout `ZaagPlannerPage`/`ZaagflowPage`) targets the wrong id and 404s silently, so planner ordering, rush flags, and job status entered since creation is lost on the next reload. The correct pattern (send the client id to the API so both sides agree) is already used in `apps/web/src/api/projects.ts:141-149` — this is the one place it wasn't applied. **Fix:** accept a client-supplied `id` in `CreateReservationSchema` (mirroring `projects.ts`), or await the POST response and remap the cache.

7. **`apps/web/src/api/{grades,profiles}.ts`** — `update`/`create`/`remove` only write into the local mock cache inside the `.catch()` (offline) branch; on a **successful** real backend response, the cache used by `listSync()` is never updated (contrast with `apps/web/src/api/machines.ts:38-73`, which correctly updates the cache on both success and fallback paths). Since kostprijs in `ArtikelPickerModal.tsx`/`RegelsTable.tsx`/`OfferteTab.tsx` is computed synchronously off `listSync()`, editing a grade's price in Instellingen leaves every other open project view quoting the old price until a full page reload. **Fix:** update the cache on the success path too, matching `machinesApi`.

8. **`apps/web/src/components/planning-queue/QueueDetails.tsx:20-28`** — the `onClose`, `onUnplan`, and `onSetHold` props are passed in from `PlanningQueuePage.tsx:331-334` but never destructured/used inside the component. Net effect: there is **no way anywhere in the Wachtrij UI to set or clear a `notBefore` hold** — a scheduler-level feature that's fully implemented in `deriveShopSchedule` and rendered (lock icon, ghost bars) but has no interactive entry point — and no way to unplan a job from the details panel except dragging it back to the backlog. **Fix:** wire the missing buttons/inputs to the already-passed callbacks.

9. **`apps/api/src/routes/{raw-materials,finished-goods,search}.ts` and `movements.ts`** don't convert Prisma `Decimal` fields before serializing to JSON (`Decimal.toJSON()` returns a **string**), while the shared Zod schemas (`raw-material.ts`, `finished-good.ts`, `movement.ts`) type these fields as `number`. The frontend had to work around this by re-declaring `RawMaterialRow`/`FinishedGood` types locally with `string` fields (`apps/web/src/api/raw-materials.ts:32-50`, `finished-goods.ts:3-12`), bypassing the shared types entirely. The fix pattern already exists in this codebase (`grades.ts:9-15`'s `serialize()`, `machines.ts:13-18`'s inline `Number(...)`) but wasn't applied to these four routes. **Fix:** add a `serialize()` helper (including nested `grade`/`profile` includes) to each of these routes.

10. **`apps/api/src/routes/low-stock.ts:19-20`** — `r.currentStock < r.minStock` compares two Prisma `Decimal`s whose `valueOf()` returns a string, so JS performs a **lexicographic** string comparison, not numeric. E.g. `currentStock = 9`, `minStock = 10` → `"9" < "10"` is `false` (character `'9' > '1'`), silently excluding a genuinely low-stock item. Currently latent (no frontend code calls this endpoint — `todoAlerts.ts` correctly recomputes low-stock client-side with explicit `Number()` conversion), but would silently corrupt results the moment this endpoint is wired up. **Fix:** `Number(r.currentStock) < Number(r.minStock)`.

11. **`packages/shared/src/schemas/raw-material.ts:25,28,29`** (`CreateRawMaterialSchema`, reused via `.omit().partial()` for updates) — `surfaceFinishId`/`locationSlotId`/`minStock` are `.optional()` only, not `.nullable().optional()`, even though the underlying Prisma columns are nullable and meant to be clearable. Since Prisma treats `undefined` as "leave untouched" and only `null` clears a column, and `RawMaterialForm.tsx:135,138,139` converts a cleared dropdown to `undefined` (enabled by this too-narrow schema), **a user can never clear these fields via the edit form** — only reassign them to a different non-null value. The same pattern also exists in `FinishedGoodSchema`'s Create/Update variants, currently latent since no finished-goods edit form exists yet. **Fix:** change to `.nullable().optional()`, matching the pattern already used correctly in `relatie.ts`, and have the form send explicit `null` for a cleared selection.

18. **Dimension validation gap** — `packages/shared/src/schemas/profile.ts:3-7` has no `min` constraint on dimension fields despite `features/34-grades-profiles.md:33` documenting one; `raw-material.ts:9,26`'s `dimensions: z.record(z.number())` accepts zero/negative values; `apps/api/src/routes/articles.ts:19` doesn't validate recipe dimensions at all (`z.unknown()`). Client-side enforcement is inconsistent (`MaterialPickerModal.tsx:107` blocks `<= 0`, `ArticleForm.tsx:188-194` uses `min={0}`, permitting 0). 4. **8x copy-pasted localStorage-cache boilerplate** — `apps/web/src/api/{grades,machines,profiles,locations,relaties,surface-finishes,company,articles}.ts` each hand-roll the same `LS_KEY`/`loadLocal`/`saveLocal`/module-cache pattern. 5. **`apps/api/src/routes/finished-goods.ts`, `packages/shared/src/schemas/finished-good.ts`, `apps/web/src/api/finished-goods.ts`, and `schema.prisma:191-207`'s `FinishedGood` model** are fully superseded by `Article` (see functionality finding #5) but remain fully alive in the codebase, still read by `search.ts`/`low-stock.ts`/Todos alerts. Already called out as unreconciled in `features/31-items-finished.md:8-13`.
