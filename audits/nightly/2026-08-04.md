## Functionality risks

### High severity

1. **`apps/web/src/routes/desktop/VoorraadPage.tsx:618`** — Reservation data is captured once and never refreshes: `const [allReservations] = useState(() => reservationsStore.list())` (verified — no setter is ever called, no `useEffect`/event subscription). Every other reservation-consuming page (`ZaagPlannerPage`, `AppLayout`, `ReserveringenPage`) listens for the `sm-reservations-changed` event or re-fetches in an effect; `VoorraadPage` does neither.
   **Failure scenario**: open `/voorraad` before the background reservations fetch resolves (e.g. right after login) — the "Gereserveerd" column and stat tiles show 0/stale values for the rest of that page's lifetime, even after data has loaded elsewhere.
   **Fix**: subscribe to `sm-reservations-changed` like `AppLayout` does, or move reservations onto an invalidatable TanStack Query key.

2. **`apps/api/src/routes/low-stock.ts:19-20`** — `r.currentStock < r.minStock` and `f.currentStock < f.minStock` compare Prisma `Decimal` objects directly with `<`. Verified: `Decimal.valueOf()` returns a string, so JS falls back to **lexicographic string comparison** (`new Decimal('9') < new Decimal('10')` → `false`). Independently found and confirmed by two separate audit passes, and reproduced live in this environment (`node -e ...` against `decimal.js-light`).
   **Failure scenario**: any item whose `currentStock`/`minStock` differ in digit-length (9 vs 10, 99 vs 100, 200 vs 1000) is silently mis-classified as low/not-low stock. The endpoint (`GET /api/low-stock`) is currently not called by the frontend (which reimplements the check correctly client-side with `Number(...)` in `utils/todoAlerts.ts`), so no user-facing alert is wrong *today* — but the bug is live and will silently corrupt results for any future caller.
   **Fix**: use `.lessThan()`/`.lt()`, or convert to `Number()` before comparing.

3. **`apps/web/src/routes/desktop/BinnenBoekenPage.tsx:52-53`** — Verified: the "Concept opslaan" and "Verwerken" buttons are plain `<button>` elements with **no `onClick` at all**. The whole page is local `useState` over hardcoded mock arrays (`SUPPLIERS`, `LOCATIONS`, `RECENT`, `INIT_LINES`) with zero imports from `api/raw-materials`, `api/movements`, or `api/locations`.
   **Failure scenario**: a user fills in a goods-receipt and clicks "Verwerken" — nothing happens, no stock is booked, no error shown. This is a core workflow (receiving material) that is entirely non-functional; matches the known status noted in `workflows/41-receive-material.md`, reported here as a concrete code-level confirmation (dead buttons, not just "different flow").

4. **`apps/web/src/api/articles.ts:214-223` + `apps/api/src/routes/articles.ts:75-104`** — Client-generated article IDs collide under concurrency and the failure is swallowed. `articlesApi.create()` computes the new ID from the local in-memory cache (`nextArtNo(cache)`) and always sends that `id` to the server; the server does have an atomic sequence generator but it's only used when `id` is omitted, which never happens from the client. The POST is fire-and-forget with `.catch(() => {})`.
   **Failure scenario**: two of the ~4 users create an article before either browser's local cache has observed the other's latest create (plausible — no websocket, only explicit query invalidation) → both compute the same `ART-00NN` → the second POST hits a unique-constraint violation on the server and is silently dropped. That browser's "new" article now exists only in local state; every subsequent edit PATCHes a nonexistent ID (404), also silently swallowed. The user keeps working believing it's saved while nothing persists.
   **Fix**: always let the server assign the ID; surface create/update failures via a notification instead of swallowing them.

5. **`apps/web/src/components/articles/ArticleForm.tsx:96-98` vs `ArticleInfoStrip.tsx:79-82` / `RelatieArtikelenTab.tsx:16`** — Two disconnected representations of "customer" on an Article. The detail page keeps `klant` (free text) and `relatieId` in lockstep via `setKlant`, but the list page's quick-edit `ArticleForm` exposes `klant` as a bare `TextInput` with no `relatieId` field, and its mutation preserves `relatieId: item?.relatieId ?? null` unconditionally.
   **Failure scenario**: from the articles list, "Bewerken" → retype `Klant` to a different company → the article's display text changes but `relatieId` doesn't, so `RelatieArtikelenTab` (which filters by `relatieId`) still lists the article under the *old* relatie and the new relatie's page won't show it at all.
   **Fix**: reuse the same relatie-Autocomplete-driven `setKlant` logic in `ArticleForm`, or drop the free-text field.

### Medium severity

6. **`apps/web/src/routes/desktop/VoorraadPage.tsx:21-27,143-145,552-571`** — `ItemDrawer`'s "Historie" section always renders a hardcoded `MOCK_HISTORY` array for every item, and `TopVerbruikDrawer`'s "mutaties" tab falls back to `MOCK_MUTATION_COUNTS`. A real endpoint (`GET /api/movements?itemId=`, `apps/api/src/routes/movements.ts:9-21`) exists but has no frontend wrapper. Actively misleading (identical fake dates/amounts regardless of the item clicked), not just an empty state.

7. **`apps/api/src/routes/movements.ts:28-68`** — No row lock (`SELECT ... FOR UPDATE`) around the read-then-write of `previousStock`/`newStock` inside the `$transaction`. Under Postgres's default Read Committed isolation, two concurrent `POST /movements` on the same item can both read the same starting stock and one update is lost. This contradicts the concurrency guarantee documented in `workflows/42-adjust-stock.md`. Low likelihood with ~4 users but a real gap between the doc's promise and the code.

8. **`apps/web/src/api/{grades,profiles,surface-finishes,locations}.ts`** — All four `.list()` wrappers swallow fetch failures and substitute hardcoded mock data (`apiFetch(...).catch(() => ({ data: mockX }))`). TanStack Query never sees the error, so a transient backend hiccup fills dropdowns with fake IDs; submitting against them causes a confusing FK-violation failure instead of a clear "couldn't load" state.

9. **`apps/api/src/routes/locks.ts:41`** — TOCTOU race in lock acquisition: `findUnique` then `create` with no upsert/transaction. Two near-simultaneous first-lock attempts on the same record can both pass the existence check and then one `create` throws an unhandled unique-constraint 500 instead of the intended 409.

10. **`apps/web/src/api/overhead.ts`** — Bedrijfskosten/machine-overhead config lives only in `localStorage` (per-browser), yet it feeds Prognose's per-machine capacity math (`planningSharedUtils.ts:31`) and the Machines cost table directly. Violates the CLAUDE.md "no new localStorage-only modules" rule and means shop-wide planning numbers can diverge by which browser/machine last edited the config.

11. **`apps/web/src/components/todos/TodoRow.tsx:22`** — The "overdue" check compares a UTC-midnight due date against local `now`, so same-day todos are flagged overdue starting ~2am CEST instead of at midnight local time.

12. **`apps/web/src/routes/desktop/InstellingenPage.tsx:57` + `apps/web/src/api/company.ts:44`** — A dead coalesce (`{naam: body.naam ?? '', ...body}`, the spread overwrites the fallback) combined with `companyApi.update()` swallowing all errors means clearing the required "Bedrijfsnaam" field can fail server-side validation silently while the UI still shows a success toast.

13. **`apps/web/src/routes/desktop/ArtikelDetailPage.tsx:140-157`** — `article.recipe` is only ever set, never cleared: if the calculator's material node is removed, the debounced save omits `recipe` from the PATCH entirely (conditional spread), so the article keeps reporting the old grade/profile everywhere (list "Grondstof" stat, detail header, form prefill) after the recipe was actually deleted.

### Low / low-medium severity

14. **`apps/web/src/components/relaties/RelatieGegevensTab.tsx:56` vs `RelatieDetailPage.tsx` `InlineNaam`** — The Gegevens tab's form only resyncs from the `relatie` prop when `relatie.id` changes, not when `naam` changes externally. Renaming a company via the header, then editing any other field on the Gegevens tab, sends the full (stale) form and reverts the just-changed name.

15. **`apps/web/src/routes/desktop/ZaagCalculatorPage.tsx:154`** — `stillNeeded || maxPieces` treats `0` as falsy: toggling on an extra bar after a cut job is already fully planned defaults its reservation to full capacity instead of 0, and the qty input's `min={1}` prevents correcting it back to zero.

16. **`packages/shared/src/schemas/raw-material.ts:33` + `apps/api/src/routes/raw-materials.ts:73-90`** — `UpdateRawMaterialSchema` allows shrinking `lengthMm` below the item's current `currentStock` with no server-side check, producing a negative-looking "Gesneden" stat and a >100%-ratio weight calculation in `VoorraadPage`'s drawer.

17. **`features/35-labels.md:38-39`** — The documented `POST /api/labels/:number/void` endpoint doesn't exist in `apps/api/src/routes/labels.ts` (only print/list/consume are implemented) and isn't listed in `03-parked.md` as deferred — a spec/code gap rather than a crash.

### Schema / type-safety drift (cross-cutting)

18. **Decimal fields serialize as strings but Zod declares them numbers** — `apps/api/src/routes/{raw-materials,finished-goods,movements}.ts` return raw Prisma rows without `.toNumber()`/`Number()` conversion on `currentStock`/`lengthMm`/`minStock`/`amount`/`previousStock`/`newStock`, so these actually go over the wire as **strings**, while `packages/shared/src/schemas/{raw-material,finished-good,movement}.ts` type them `z.number()`. The frontend works around this by defining its own separate `RawMaterialRow`/`FinishedGoodRow` types with `string` fields instead of using the shared Zod-inferred types — meaning the shared schemas are effectively inaccurate/unused for these three domains. Inconsistent with `grades.ts`/`machines.ts`, which correctly convert (`Grade.densityKgM3` comes back as a number from `/grades` but as a string when embedded in a raw material's nested `grade` relation). **Medium severity** — no crash today because nothing currently does numeric arithmetic directly on these API responses without an explicit `Number()`, but it's a real, silent contract violation that will bite the next feature that trusts the Zod type.

19. **`Grade.pricePerKg`** — `.optional()` in the Zod schema but **nullable** (not optional) in the Prisma model and in actual API responses. Low severity but a real type-vs-reality mismatch (`undefined` vs `null` handling can differ in consuming code, e.g. `?? 0` vs `!== undefined` checks).

20. **No shared Zod schema for `Article` or `ZaagReservering`** — 2 of 21 Prisma models have no corresponding schema in `packages/shared`. `Article`'s JSON columns (`recipe`, `operations`, `notes`, `attachments`, `estimate`) are typed `z.unknown()` ad hoc in the route file and never structurally validated server-side — malformed payloads for the very structures that drive pricing are accepted and stored as-is. Low-medium severity (design gap, not an observed crash).

21. **Weight-computed-on-read invariant implemented twice** — `apps/api/src/services/weight.ts` and `apps/web/src/api/raw-materials.ts` (`computeWeightKg`) both implement the "never stored, computed from profile+dimensions+density" formula independently, with a subtle NaN-vs-0 difference for missing dimensions. The core invariant itself holds (verified: no `weight`/`gewicht` column in `schema.prisma`), but the duplicate implementation is a drift risk. Low severity.

22. **Unvalidated casts masking potential drift** — `apps/api/src/routes/projects.ts` casts `row.status as Project['status']` with no DB-level enum constraint on the column; `apps/api/src/routes/todos.ts`'s `serialize(t: any)` and `apps/web/src/api/overhead.ts`'s `JSON.parse(raw) as any` disable type checking on data that should be structurally typed. Low severity individually, flagged as a pattern worth tightening.

**Checked and clean**: response-shape convention (`{ data }` / `{ error: { code, message, details? } }`) — spot-checked across all route files including the error middleware, no violations found. `apps/web/src/api/*.ts` all funnel through one `apiFetch`/`apiUpload`. Zod validation + error handling in `apps/api/src/routes/*.ts` is uniform via `Schema.parse()` + one shared `errorMiddleware`.

### Medium severity

5. **Currency formatter duplicated verbatim in 10 places** — identical `€ ${n.toLocaleString('nl-NL', {minimumFractionDigits:2, maximumFractionDigits:2})}` logic independently reimplemented in `ArticleFinancialCard.tsx`, `ArticleCalculator.tsx`, `ArticleSankey.tsx`, `BedrijfskostenTab.tsx`, `OverheadTab.tsx`, `ArtikelenPage.tsx`, `apps/web/src/api/projects.ts`, `apps/web/src/services/offerte-pdf.ts`, `apps/web/src/services/opdrachtbevestiging-pdf.ts`, and `apps/api/src/services/offerte-pdf.ts`. 8. **`apps/api/src/routes/sequences.ts`** — `/api/sequences/next` is mounted but never called by the frontend; `projects.ts` and `articles.ts` instead duplicate its exact `doc_sequences` SQL inline. Either use the endpoint or remove it.

9. **Dutch long-date formatter duplicated 4×** — identical `toLocaleDateString('nl-NL', {day:'2-digit', month:'long', year:'numeric'})` in `offerte-pdf.ts` (web), `opdrachtbevestiging-pdf.ts`, `productie-pdf.ts`, and `apps/api/src/services/offerte-pdf.ts`.

11. **`apps/web/src/routes/desktop/InstellingenPage.tsx:406`** — "Nummering" and "Meldingen" settings tabs are fully static mock UI with no backend wiring, left over from before the mock phase ended.

12. **`apps/web/src/components/settings/OverheadTab.tsx:129`** — machines data is fetched via two independent, non-synchronized caches (a TanStack Query here vs. the module-level `listSync()` cache used by Planning/Prognose), risking the two views showing different machine data after an edit.
