## Functionality risks

### High

1. **Low-stock detection compares `Decimal` values as strings, not numbers.**
   `apps/api/src/routes/low-stock.ts:19-20` does `r.currentStock < r.minStock` on Prisma `Decimal` fields. Prisma's `Decimal.valueOf`/`toJSON` return a **string**, so JS falls back to lexicographic comparison. Example: `currentStock=950, minStock=1000` → `"950" < "1000"` is `false` ('9' > '1'), so a numerically-low item is silently excluded. Independently confirmed by two auditors.
   *Currently mitigated in practice*: no frontend code calls `/api/low-stock` today (`apps/web/src/utils/todoAlerts.ts` recomputes low-stock alerts client-side with correct `Number()` conversions) — but the endpoint is live and mounted, and any future/other consumer would get silently wrong results.
   → Fix: use `.toNumber()` or Decimal's `.lt()` instead of the raw `<` operator; consider removing the endpoint if it's dead (see Redundancy).

2. **Mutation API wrappers swallow real backend failures and report fake success.** Systemic pattern across `apps/web/src/api/{grades,profiles,surface-finishes,locations,machines,company,relaties,articles}.ts` and parts of `projects.ts`: every `create`/`update`/`remove` wraps the real `apiFetch(...)` call in `.catch()` and silently falls back to writing the change into an in-memory/localStorage-only mock, resolving as success. `apiFetch` (`apps/web/src/api/client.ts:61-64`) throws on **any** non-2xx response — validation errors, unique-constraint violations, `403` from `requireAdmin`, and its own 3s timeout — not just genuine outages.
   Concrete scenarios: a non-admin's "Locatie aanmaken" is correctly rejected server-side with 403, but `locationsApi.createLocation` swallows it and `LocationsTab` shows a green success toast — the location only exists in that one browser's `localStorage`, invisible to the other 3 workstations on the LAN (`apps/web/src/api/locations.ts:86-127`). Renaming a Grade to a name that violates a unique constraint behaves the same way (`grades.ts`) — the "saved" edit silently disappears on next reload once `initGrades()` refetches the real list. This directly contradicts the documented 2026-06-22 "mock phase ended" decision (no new localStorage-only write paths).
   → Fix: don't catch-and-fake-success on write operations; let mutation errors propagate so `onError` handlers actually fire. A read-only fallback for `list()` may still be reasonable.

3. **Reservation data goes stale because several pages seed it once and never subscribe to change events.** `apps/web/src/routes/desktop/VoorraadPage.tsx:618`, `ZaagCalculatorPage.tsx:70`, and `ZaagflowPage.tsx:527` all do `useState(() => reservationsStore.list())` and never listen for the `sm-reservations-changed`/`storage` events that `apps/web/src/api/reservations.ts:60` fires on every create/complete. `ZaagPlannerPage.tsx:41-62` shows the correct pattern already exists elsewhere in the same feature area — it explicitly subscribes to both events.
   Concrete risk: two users with the Zaag Calculator and/or Voorraad open concurrently won't see each other's reservations, so calculated "available length" can double-book or over-cut the same physical bar; a job created via the Calculator may not appear on the Zaagflow board until an unrelated re-render happens.
   → Fix: subscribe to `sm-reservations-changed`/`storage` in `VoorraadPage`, `ZaagCalculatorPage`, and `ZaagflowPage` the same way `ZaagPlannerPage` already does.

4. **`accepteerOfferte` client/server id mismatch can silently drop production-order updates.** `apps/web/src/api/projects.ts:345-415` generates `productieOrder`/`Opdrachtbevestiging` ids locally (`nextLocalDocId('PROD'/'OB')`) for optimistic UI, but the POST body only sends `{ userName }` — the server (`apps/api/src/routes/projects.ts:312-384`) independently generates its own ids with no coordination, unlike every other mutation in this file which sends a client-generated id the server is designed to honor. If a user checks off a productie stap or marks an order gereed before the accept-POST's background sync overwrites the optimistic cache, the request targets an orderId/stapId the server has never seen; the server's lookup finds no match and returns an unchanged project with `200 OK` — no error is surfaced, and the checkmark silently reverts or is lost.
   → Fix: have the client send its generated `productieOrders`/`opdrachtbevestiging` ids in the accept request body, honored server-side the same way `POST /projects` already does for project ids.

5. **Client-generated article IDs bypass the atomic sequence, risking silent collisions.** `apps/web/src/api/articles.ts:200-223`'s `nextArtNo()` computes the next number from the locally cached article list and sends it explicitly as `id` in the create POST, bypassing the backend's atomic `doc_sequences`-backed generator (`apps/api/src/routes/articles.ts:48-56,79`). The app supports detached popout windows (each an independent JS realm with its own cache), so two near-simultaneous creates (two users, or two windows) can compute the same next number; the second POST hits the unique-constraint on the Article PK and fails — and per finding #2, that failure is swallowed, so the second article silently vanishes on reload.
   → Fix: let the server always assign the article ID, or reserve it via the atomic sequence before creating.

### Medium

6. **`gradesApi`/`profilesApi` `listSync()` caches go stale after edits, silently feeding wrong prices into kostprijs calculations.** Unlike `machinesApi.list()` (`apps/web/src/api/machines.ts:41-43`), which updates its module-level cache on every successful fetch, `gradesApi.list()`/`profilesApi.list()` (`grades.ts:45-46`, `profiles.ts:71-72`) never write back to the cache `listSync()` reads. Per CLAUDE.md's documented convention, kostprijs in `ArtikelPickerModal`/`RegelsTable`/`OfferteTab` is computed via `buildEstimateCtx`+`computeEstimateTotals` using `gradesApi.listSync()`/`profilesApi.listSync()` directly (not through TanStack Query), so editing a Grade's `pricePerKg` in Settings updates the Settings table (via query invalidation) but the calculator keeps quoting the old price until a full page reload.
   → Fix: update the module cache in `list()`'s success path like `machines.ts` does, or read through the TanStack Query cache instead of a parallel module-level cache.
7. **Same root cause, broader pattern: several Productie components read `listSync()`/direct calls instead of subscribing via `useQuery`**, so `invalidateQueries` after the app's startup fetch (`useInitAppData.ts`) is a no-op for them — e.g. `OfferteTab.tsx:236-238`, `ArtikelPickerModal.tsx:65-68`, `OpdrachtbevestigingTab.tsx:43,48-50`, `ProjectenPage.tsx:60`, `ProjectDetailPage.tsx:98`, and `RelatieDetailPage.tsx:76-80` (KPI strip, contrast with `RelatieArtikelenTab.tsx:10-13` which correctly uses `useQuery` for the identical data). Opening these views in the first second or two of a cold load can compute prices/counts from hardcoded mock seed data with no visual indicator and no automatic refresh.
   → Fix: route these reads through `useQuery` consistently, as `OverheadTab.tsx:129` already does correctly for machines.
8. **Raw materials / finished goods return `Decimal` fields as unconverted JSON strings, contradicting the shared Zod schema's declared `number` type.** `apps/api/src/routes/raw-materials.ts`'s `withWeight()` and `finished-goods.ts` never call `.toNumber()` on `lengthMm`/`currentStock`/`minStock` (or nested `grade`/`profile` relations), unlike `grades.ts`/`machines.ts`/`articles.ts` which do. The frontend already works around this by hand-typing these fields as `string` in `RawMaterialRow`/`FinishedGoodRow` and wrapping every use in `Number(...)` (20+ call sites in `VoorraadPage.tsx`), so there's no live break today — but the "single source of truth" shared schema is simply not honored, and new code written directly against the shared type would do string concatenation instead of arithmetic.
   → Fix: add a `serialize()` step in these two routes that converts Decimal fields, matching the pattern already used elsewhere.
9. **`MutatieModal`'s help text tells users the wrong unit.** `apps/web/src/routes/desktop/VoorraadPage.tsx` (~line 377-379): the field is labeled "Lengte (mm)" with a `mm` suffix, but its description reads "Voer de lengte in meters: 1 m = 1000 mm". A user who types `6` intending 6 m gets a 6 mm mutation applied — a real, direct-to-inventory data-entry risk.
   → Fix: correct the description to match the mm unit actually used.
10. **`MutatieModal`'s "Toevoegen" (add stock) has no upper bound against the bar's original length**, while the drawer's weight readout (`VoorraadPage.tsx:500`, `weightKg * remaining/original`) is not clamped either (elsewhere on the page the remaining/original ratio *is* clamped for the percentage bar). An operator correction via "Toevoegen" can push `currentStock` above `lengthMm`, after which the displayed weight exceeds the bar's physical maximum.
    → Fix: cap "toevoegen" at the original length, or clamp the weight calc consistently with the percentage bar.
11. **`ItemDrawer`'s "Historie" section shows identical fabricated data for every material**, regardless of which row is open (`VoorraadPage.tsx:21-27` `MOCK_HISTORY`, rendered unconditionally at lines 552-571) — every item appears to share the same 5 fake movements (e.g. `ONT-2026-0418`) as if it were real audit trail, even though the mock phase has formally ended and a real `/api/movements` endpoint already exists.
    → Fix: wire to `GET /api/movements?itemId=...` or remove the section until it is.
12. **`locationsApi` mutation fallback can let a form submit a nonexistent `locationSlotId`.** If `locationsApi.list()` transiently fails and falls back to hardcoded `MOCK_LOCATIONS` slot ids, `RawMaterialForm.tsx` can submit one of those fake ids to `rawMaterialsApi.create/update`, causing an opaque FK failure instead of a clean validation message. Direct consequence of finding #2/#3.
13. **`Article.relatieId` has no FK/cascade, so deleting a relatie leaves dangling references contradicting the UI's own copy.** The delete-confirmation dialog in `RelatiesPage.tsx:150-152` tells the user linked articles "verliezen de relatiekoppeling," but `Article.relatieId` in `prisma/schema.prisma` has no `@relation`/cascade, and neither `relatiesApi.remove` nor `DELETE /relaties/:id` nulls it out. `ArtikelDetailPage.tsx:201` then silently resolves the missing relatie to `null` with no indication of what happened.
    → Fix: add a real FK with `onDelete: SetNull`, or explicitly null `relatieId` on affected articles in the delete route.
14. **No shared Zod schema exists for `Article`**, unlike every sibling Stamgegevens model (grade, profile, relatie, surface-finish, finished-good). `apps/api/src/routes/articles.ts:9-28` validates `recipe`/`operations`/`notes`/`attachments`/`estimate` as `z.unknown()`, with zero runtime shape enforcement against the hand-maintained frontend `Article`/`ArticleRecipe` interfaces. Concretely, if `recipe` is ever persisted without `dimensions`, `ArtikelenPage.tsx:100-105`'s `formatRecipe()`/`formatDimensions()` will throw on `dims.diameter`/`dims.width`, crashing the whole Artikelen list render.
    → Fix: add a shared `ArticleSchema`/`ArticleRecipeSchema` (at least for `recipe`) and validate it server-side.
15. **`buildJobs()` collapses unrelated sawing sessions into one job when `calculatieNr` is blank.** `apps/web/src/api/zaag-jobs.ts:19-48` groups all reservations with no `calculatieNr` into a single `'—'` bucket and takes the displayed machine/materiaal/diameter from `items[0]` only. Since `calculatieNr` is explicitly optional in the Calculator UI, two unrelated sessions left blank display as one job with a misleading combined header on the Planner/Zaagflow board (the per-bar cut logic itself still uses each bar's own fields, so this is a display/grouping defect, not a mis-cut).
    → Fix: group by a synthetic per-reservation key when `calculatieNr` is blank, instead of a shared bucket.
16. **Todos "overdue" check compares raw timestamps instead of calendar dates**, per the Planning audit (`apps/web/src/components/todos/TodoRow.tsx:22`). Since due dates are stored as UTC midnight, a task due "today" reads as overdue for nearly the entire business day in the Netherlands timezone.
    → Fix: compare calendar dates (local midnight-to-midnight), not raw `Date` instants.
17. **Converting a Signalering to a todo has no dedup check.** `apps/web/src/routes/desktop/TodosPage.tsx:52` — repeated clicks on "Zet als taak" create duplicate tasks indefinitely, with no check against existing todos for the same signalering.
    → Fix: check for an existing todo referencing the same signalering before creating another.
18. **Prognose bar chart and heatmap can disagree on machine capacity in "Maand" view.** `apps/web/src/components/prognose/PrognoseBars.tsx:76` uses an averaged `capacityByMachine`, while `PrognoseHeatmap` uses the exact `capacityPerPeriod`. Since months have variable lengths, the two visualizations can show contradictory over-capacity signals for the same period.
    → Fix: derive both charts from the same exact per-period capacity calculation.

## Code redundancy

### High/Medium

19. **The Planning Queue's "hold" feature has no UI entry point.** `apps/web/src/components/planning-queue/QueueDetails.tsx:26` receives `onClose`, `onUnplan`, and `onSetHold` props but never calls them; `projectsApi.setHold` has zero other callers repo-wide. The notBefore/hold mechanism is fully implemented in the scheduler and rendered (lock icon) in `QueueTimeline`, but a user can never actually set it. Same component: "Artikel"/"Tekening"/"Verkenner" buttons have no `onClick` handler at all (only "Project" works), and the "SHIFT" column's input updates local state that nothing downstream consumes.
    → Fix: wire the missing handlers, or remove the dead buttons/props if the feature isn't meant to ship yet.
20. **Systemic ~25-line localStorage-fallback CRUD boilerplate duplicated 5-6× across `apps/web/src/api/{grades,profiles,surface-finishes,locations,machines}.ts`** — same `loadStore/saveStore/mock array/listSync/list/create/update/remove` shape repeated with only the entity name changed. This is also where findings #2/#6 live, so consolidating would fix the bugs and the duplication together.
    → Fix: extract a generic `createCachedCrudApi<T>(resource, mockSeed)` factory (or, better per finding #2, drop the write-path fallback entirely and keep only a thin read cache).
21. **`ArticleForm.tsx`'s entire "add" mode is dead code.** Verified via grep that the component is only ever rendered once, always with `mode="edit"` (`ArtikelenPage.tsx:371`); real article creation goes through `handleNieuwArtikel()` + `ArtikelPickerModal`, bypassing this form. The `mode==='add'` branch (auto-number display, "Artikel toevoegen" title, `nextArtNo` usage, `articlesApi.create` arm) is unreachable.
    → Fix: delete the unreachable add-mode branch, or wire it up and remove the duplicate creation path.
